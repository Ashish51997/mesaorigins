# Mass Polimer ERP — Production-Readiness & Workflow Audit

> **Scope:** Full end-to-end audit of every user workflow across all 10 roles and ~45 screens, tracing whether each stage actually hands off to the next and whether the app is safe/complete to run in production.
> **Method:** Direct read of the app shell, backend, and persistence layer, plus six parallel deep-dive audits (Auth/Persistence, Sales/CRM, Planning/PPC, Manufacturing/Logbook, Quality/Inventory/Store, Dispatch/CAPA/Trace/ACL).
> **Verdict up front:** This is an excellent, richly-featured **click-dummy / prototype**. It is **not** production-ready. The blockers are structural (no real auth, no per-tenant data isolation, client-only authorization, single shared JSON store, and several workflows that look interactive but don't hand off downstream). None of these are quick patches — they are the difference between a demo and a system of record.

## How to read this

Each finding is tagged with a severity and points at real code:

- **Blocker** — must be fixed before any real user touches it (security, data loss, or a workflow that structurally cannot complete).
- **High** — breaks or badly weakens a core flow; a real user hits it on day one.
- **Medium** — incorrect/confusing behaviour or missing validation; workable but not shippable.
- **Low** — polish, hygiene, tech-debt.

Format: **[Severity] Title** — `file:line` — what's wrong · flow/impact · fix.

## Executive summary (the shape of the problem)

The app is built as a **single-user in-browser prototype** wearing an ERP's clothes. The recurring, systemic issues are:

1. **No real authentication or authorization.** Login is role-pick; Google sign-in makes *anyone* a Managing Director; all permission checks are client-side cosmetics; the backend and Firestore are world-readable/writable. *(See Auth section — 3 blockers.)*
2. **No data isolation or concurrency safety.** One global `data.json` (committed to git), shallow last-write-wins merge, every client auto-POSTing its whole state every second, plus a second uncoordinated writer. Two users = silent data loss.
3. **Two source-of-truth backends that never reconcile** (Firestore when Google-signed-in, `data.json` otherwise). Switching auth state switches the entire dataset.
4. **Duplicated, divergent implementations of the same domain** (`SalesModule` vs `sales/SalesScreens`, `Planning` vs `planner/PlannerScreens`, `QualityPacking` vs `quality/QualityScreens`, `InventoryModule` vs `store/StoreScreens`). Role A and Role B act on the same records through different code with different fields/status strings.
5. **Broken cross-module handoffs.** Several workflows produce records that the next stage never consumes (the value chain of *order → plan → logbook → QA → inventory → dispatch → trace* has gaps). See each module section.
6. **Prototype-grade UX for real actions** — native blocking `alert()` for success/errors, `Date.now()+Math.random()` IDs, mostly-untranslated i18n, 40 stray `console.*`.

## Cross-cutting infrastructure (verified directly)

- **[Blocker] One global, unauthenticated datastore shared by everyone** — `server.ts:206-229`, `server.ts:46` — `/api/data` GET/POST read and overwrite a single `data.json` in the process CWD with no auth, tenant, or user scoping, bound to `0.0.0.0:3000`. Flow/impact: every "user" of the non-Firebase path shares one dataset; there is no notion of *my* orders vs *yours*. Fix: real per-tenant persistence behind an authenticated API.
- **[Blocker] Concurrent saves clobber each other (shallow merge + 1s full-state POST)** — `server.ts:218-221`, `src/App.tsx:397-437` — POST does `{...current, ...incoming}`, replacing whole arrays per key; every client debounce-POSTs its *entire* state every 1s. Flow/impact: two people editing → each 1-second save overwrites the other's collections; a client momentarily holding an empty array wipes it for all. Fix: authenticate + record-level patch/optimistic concurrency, not array replacement.
- **[High] A second, uncoordinated writer of the shared blob** — `src/components/ManufacturingStandards.tsx:181,206` — ManufacturingStandards fetches and POSTs `/api/data` on its own, outside App's lifted state, racing App's auto-save. Flow/impact: BOM/recipe edits and App-state edits clobber one another. Fix: single writer; route all persistence through one store.
- **[High] Two source-of-truth backends never reconciled** — `src/App.tsx:317-394` — Firestore is used when `user.isFirebase`, `data.json` otherwise; data created under one is invisible under the other and there's no migration/merge. Flow/impact: signing in with Google shows a different universe of data than role-pick. Fix: one backend, or an explicit sync/migration path.
- **[Medium] Runtime datastore committed to source control** — `data.json` is tracked and rewritten every second (`server.ts:190-196`), which is *why* `vite.config.ts` must exclude it from the watcher. Flow/impact: constant working-tree churn, accidental commits of live data. Fix: `.gitignore` it; treat as runtime state.
- **[Medium] Native blocking `alert()` used for real success/error feedback** — `src/components/Reports.tsx:87`, `src/components/CapaComplaints.tsx:88,98,124,139`, `src/components/DispatchModule.tsx:74,283`, `src/components/QualityPacking.tsx:227,229` — Core actions confirm via `alert()`, bypassing the app's own `ToastHost`/`pushToast`. Flow/impact: jarring, blocks the UI thread, untestable, not production UX. Fix: route through the existing toast system.
- **[Medium] Collision-prone client IDs** — e.g. `src/components/AclManagement.tsx:87`, `src/components/MigrationHub.tsx:132` — records keyed by `Date.now()+Math.random()`. Flow/impact: rapid creation or clock skew → duplicate IDs → overwritten records. Fix: server-issued IDs or `crypto.randomUUID()`.
- **[Low] i18n is a stub** — `src/lib/i18n.ts:3` — only ~10 labels translated to KN/HI though the header offers EN/KN/HI. Flow/impact: non-English users get a mostly-English UI. Fix: complete the dictionaries or scope the switcher down.
- **[Low] 40 stray `console.*` statements** across `src/` — remove or gate behind a logger before shipping.
- **[Low] Single 1.59 MB JS bundle, no code-splitting** — `npm run build` warns chunks > 500 kB. Flow/impact: slow first load. Fix: route-level `React.lazy`/dynamic import + `manualChunks`.

## Auth, Session & Persistence

- **[Blocker] Google sign-in hardcodes every user to Managing Director** — `src/App.tsx:298` (and `:302`) — The `onAuthStateChanged` handler builds the session with `role: 'Managing Director'` and calls `setCurrentRole('Managing Director')` for *any* Google account that completes the popup, ignoring who signed in. Flow/impact: any Google user who can open the OAuth popup lands as the highest-privilege role with the full admin/MD menu — no allow-list, domain check, or role lookup. Fix: resolve the signed-in email against the employee directory and reject unknown accounts; never assign a role from a constant.
- **[Blocker] Firestore security rules allow any authenticated user full read/write of all data** — `firestore.rules:10-57` — Every collection is gated only by `allow read, write: if request.auth != null`, and `firebaseSync.ts` uses the client SDK directly. Flow/impact: with the hardcoded-MD sign-in above, any Google account can read and overwrite the entire company dataset from the browser. Fix: enforce per-collection role/UID checks server-side; don't rely on `auth != null`.
- **[Blocker] Backend `/api/data` has zero authentication** — `server.ts:206-229` — No auth middleware on GET/POST; anyone reaching the port fetches the full dataset and POSTs arbitrary overwrites. Fix: require an authenticated session on both routes.
- **[Blocker] "Login" is role-selection only — no real authentication** — `src/components/LoginScreen.tsx:38-47` — Picking a role calls `onLogin` with a fabricated `uid: demo-${role}` and synthesized email; no password/OTP/identity check. Flow/impact: any visitor becomes any role, including `Administrator`. Fix: fine for a click-dummy, must never ship — gate real deployments behind identity verification.
- **[High] All authorization is client-side; localStorage trusted unverified** — `src/App.tsx:163-168`, `src/lib/accessStore.ts:43-51`, `src/lib/aclUtils.ts:19-49` — `currentRole` comes straight from `localStorage.erp_session.role`; `can()` only hides menu items/screens. Flow/impact: edit `erp_session`/`mp_grants` in devtools to become Administrator; nothing server-side re-checks. Fix: treat client ACL as cosmetic; enforce every permission server-side.
- **[High] `can()` returns `true` when no employee context is set** — `src/lib/accessStore.ts:48-51` — `if (!current) return true;` grants all permissions until `setCurrentEmployee` runs after first render (`App.tsx:246-252`). Flow/impact: on initial mount every check passes, briefly exposing restricted UI. Fix: default-deny until context is established.
- **[High] The offline "send queue" carries no real data and never resends** — `src/lib/offline.ts:13-42`, `src/App.tsx:341-344,465-467` — `enqueue` stores only `{id,label}`; `flushQueue` slices the array on a 700ms timer and toasts "sent"; real saves just `catch`+`console.error` with no retry. Flow/impact: an operator entering readings offline sees "all sent" while the data is silently dropped — data loss disguised as success. Fix: queue real payloads and replay on reconnect, or remove the fake queue UI.
- **[Medium] `inactive` status does not block sign-in** — `src/lib/userStore.ts:93-94` — Role-pick login never calls `canSignIn`; `employeeForRole` falls back to any matching role even if `inactive`. Flow/impact: deactivated employees remain fully usable. Fix: check `canSignIn` at login; exclude inactive employees.
- **[Medium] Firebase project config committed** — `firebase-applet-config.json:1-11` (tracked) — `apiKey`, `oAuthClientId`, `authDomain`, `projectId` for a live GCP project checked in. Web keys are identifiers not secrets, but with `auth != null`-only rules this file is enough to read/write the DB. Fix: restrict the API key (HTTP referrer + API restrictions) and OAuth client to known origins; tighten Firestore rules.
- **[Medium] Hardcoded personal Gmail as fallback identity** — `src/App.tsx:294,1203`, `src/components/AclManagement.tsx:338` — `aroul303@gmail.com` is the fallback `user.email` and the ACL/audit author; `displayName` defaults to `'Authorized Admin'`. Flow/impact: a real person's email is baked into the bundle and recorded as the actor for ACL/audit entries. Fix: derive identity solely from the verified session or fail closed.
- **[Medium] Role-pick sessions aren't restored on reload — only the role is** — `src/App.tsx:227-234` vs `:163-172` — `user` always inits to `null`, so a non-Firebase user is bounced to LoginScreen on every refresh even though `currentRole` rehydrates from `erp_session`. Flow/impact: the persisted session is effectively dead. Fix: restore the full non-Firebase session on mount, or stop writing it.
- **[Low] Live `data.json` committed and rewritten every second** — tracked file; `server.ts:190-196`, `App.tsx:443-470` — mutable datastore under version control. Fix: gitignore and treat as runtime state.

## Sales & CRM Flow

> **Core lifecycle works:** `inquiries/salesOrders/customers/complaints` and their setters are shared lifted state passed to both SalesScreens and Planning, so confirming an order creates a `'pending'` SalesOrder that appears in Planning's queue, and Planning setting it `'planned'` flows back to the Sales board. Adding a customer is visible everywhere. Status strings are consistent across Sales/Planning/types. The defects below are duplication, dead code, and validation gaps.

- **[High] Confirmed orders re-enter the quotation queue and can be re-ordered (duplicate/orphan SalesOrders)** — `src/components/sales/SalesScreens.tsx:184` (and `:50`) — `Quotations.toQuote`/`SalesHome.needQuote` filter `status === 'submitted' || 'approved'`, but `Orders.confirm` sets the inquiry to `'approved'` after booking (`:222`). So a just-confirmed order's inquiry reappears "waiting for a quotation"; re-quoting it puts it back in Orders where `confirm` (`:218-225`) mints a *second* SalesOrder for the same inquiry with no dedupe. Seed `inq-2` is already `'approved'` with `SO-2026-102`, so it's visible on first load. Flow/impact: normal clicks silently create duplicate orders that all flow into planning. Fix: give a booked inquiry a terminal status (e.g. `'ordered'`) or filter `toQuote`/`needQuote` to `'submitted'` only, and block confirm when an SO already references the inquiry.
- **[Medium] Length-based ID generation reuses SO/inquiry numbers after cancel** — `src/components/sales/SalesScreens.tsx:220` — `soNumber = SO-2026-${150 + salesOrders.length}`; `Orders.cancel` (`:227-231`) removes the SO so the array shrinks and the next confirm regenerates the identical number. Same for `inquiryNumber` (`:112`) and the monolith (`SalesModule.tsx:91,145`). Flow/impact: two orders can share a number that is also the Batch-Passport trace key, so tracing/reporting collides. Fix: monotonic counter or uuid, never `array.length`.
- **[Medium] 'draft' inquiries are a dead-end in the Sales Executive UI** — `src/components/sales/SalesScreens.tsx:184` — nothing transitions `draft → submitted` in SalesScreens and Quotations excludes `draft`, so seed `inq-3` (`'draft'`) can never be quoted or ordered; only the (unreachable) monolith has the "Submit specs" button. Flow/impact: any draft inquiry is stranded. Fix: add a submit action on the Inquiries list, or create/seed inquiries as `'submitted'`.
- **[Medium] The entire parallel monolith (`SalesModule.tsx`, `Customers.tsx`) is unreachable dead code** — `src/App.tsx:644,1020-1035,670-675` — the `'sales'`/`'customers'` modules activate only via `handleActiveTabFromDashboard`, passed only to the generic `<Dashboard>` fallback, which fires only when `currentRole` is none of the 8 canonical roles — but `currentRole` is always `normalizeRole`'d, so it never fires. Flow/impact: features living *only* in the monolith — discount/negotiation with audit note, printable SO PDF, customer editing, GST-uniqueness, active/inactive toggle, per-customer order history — are dead for every user. Fix: delete the monolith, or wire a real entry point if those features are wanted.
- **[Medium] New complaints trace to a dead key and fabricate the customer/product** — `src/components/sales/SalesScreens.tsx:364` (trace at `:404`) — `submit` builds `complaintNumber = C-${105 + complaints.length}` (→`C-107`), which has no `BatchLineage` alias (only seed `C-104` does), yet the trace button calls `onTrace(c.complaintNumber)`; the chosen invoice (`INV-…`, which *does* resolve) is stored in `batchNumber` but never used for tracing. It also hardcodes `customerId` to `customers[0]` and `product` to `'RPVC roll'`. Flow/impact: clicking a real complaint dead-ends the Batch Passport, and every complaint is filed against the wrong customer with a placeholder product. Fix: trace by the invoice/batch alias and derive customer+product from the selected invoice.
- **[Low] Dead "Take a photo of the defect" button** — `src/components/sales/SalesScreens.tsx:378` — the camera button has no `onClick`; `CustomerComplaint.photoUrl` is never set. Fix: wire a file/camera `<input>` like the Inquiries attachment (`:158`).
- **[Low] SalesHome "Order status board (advancing live)" is disconnected theater** — `src/lib/salesFlowStore.ts:21-25` — the board renders hardcoded demo orders unrelated to real `salesOrders`; a confirmed real order never appears, and Dispatch's release hardcodes `markDispatched('SO-2026-141')` (`DispatchScreens.tsx:134`) regardless of what shipped. Fix: drive the board from `salesOrders`, or label it a demo ticker.
- **[Low] Divergent customer validation between the two add paths** — `src/components/sales/SalesScreens.tsx:309-326` vs `src/components/Customers.tsx:39-49,60-77` — the reachable SalesScreens modal requires only `name` with no GST-uniqueness check, while the (dead) monolith enforces contact/phone/email/address + unique GST. Flow/impact: customers created by Sales can carry blank or duplicate GST. Fix: apply the same required-field + GST-uniqueness validation in `AddCustomerModal`.

## Planning / PPC Flow

> **Happy path does connect:** a confirmed order (`SalesScreens.tsx:220`, `status:'pending'`) appears in `OrdersToPlan`/`PlannerHome`, and a created plan (`status:'scheduled'`, `salesOrderId` set) flips the order to `planned` and is picked up by `LogbookModule`. The defects below are in validation, date-handling, material logic, and the duplicate implementation — not a broken end-to-end wire.

- **[Blocker] Machine/shift can be double-booked by changing the run date after selecting a slot** — `src/components/planner/PlannerScreens.tsx:115` — `PlanOrderModal.confirm()` builds the plan from the current `date`+`sel` but never re-checks `occupancy()`; the date input (line 155) changes `date` without resetting `sel`, so you can pick a free cell on date A, switch to date B where that machine+shift is booked, and confirm. Flow/impact: two plans on the same line+shift+date, both flow into the Logbook, giving the operator an impossible schedule. `Planning.tsx:63-74` re-validates at submit — the new screen regressed. Fix: re-run `occupancy(sel.machine, sel.shift)` against the chosen date inside `confirm()`, and clear `sel` in the date `onChange`.
- **[High] "Today's plan", capacity bars, and Machine Capacity ignore the plan date entirely** — `src/components/planner/PlannerScreens.tsx:283` — `PlanView`, `CapacityBars` (317), and `MachineCapacity` (484) scan `productionPlans` with no date filter yet are labelled "Today's plan"/"shifts booked today". Flow/impact: the seeded plan (2026-07-14) and every future plan show as booked "today" forever, so live capacity is wrong the moment any plan is on another day. Fix: filter to `scheduledStartDate.split('T')[0] === todayISO` with a date selector.
- **[High] Planning any non-PVC order consumes RPVC raw material (wrong BOM)** — `src/components/planner/PlannerScreens.tsx:37` — `activeFormulaFor()` maps by regex (`/rpvc/`→RF03, `/spvc/`→SF13, else RF03); LDPE orders fall through to RF03, so `confirm()` (130-131) deducts RPVC resin/CaCO3/Stabilizer for an LDPE order. Flow/impact: Material Availability drops the wrong lots, understating RPVC and never touching the LDPE lot actually needed. Fix: resolve the formula from the order's real product/family (or the machine's `currentFormula`); skip consumption when no formula matches instead of defaulting.
- **[High] Two divergent planning implementations, both live** — `src/components/Planning.tsx:17` vs `src/components/planner/PlannerScreens.tsx:106` — both write `productionPlans` but with different rules: old requires operator name + re-validates double-booking + offers Release; new requires no operator, has no release, adds due-date/capacity warnings. Generic `planning` module renders the old one (App.tsx:1102); the Production Planner role renders the new ones. Flow/impact: the same order is scheduled under inconsistent rules depending on who opens it. Fix: retire `Planning.tsx` (or make the planner screens the single implementation).
- **[Medium] No operator is ever assigned in the planner flow** — `src/components/planner/PlannerScreens.tsx:120` — `operatorName` is hard-coded to `'(assigned at shift start)'` with no picker, and `blankLogbook` (LogbookModule.tsx:46) strips the `(`-prefixed placeholder, so the logbook opens with a blank operator. Flow/impact: a scheduled plan links to a machine but never a person; shift accountability is lost. Fix: add an operator/shift-crew selector persisted on the plan.
- **[Medium] Past run dates allowed with no warning** — `src/components/planner/PlannerScreens.tsx:155` — no `min` on the run-date input; the only guard warns when `date > deliveryDate`. `Planning.tsx:25` is worse — defaults `selectedDate` to a hard-coded past date `'2026-07-13'`. Flow/impact: "scheduled" plans dated in the past appear bookable/today. Fix: `min={todayISO}` and block/confirm past-dated runs.
- **[Medium] RM consumption is irreversible and not reconciled on release/re-plan** — `src/lib/plannerStore.ts:74` — `consumeLot()` only decrements; `Planning.tsx:99` release resets the order to `pending` but never restores lots, and the planner screens have no release at all. Flow/impact: plan→release→re-plan permanently drains RM (and double-deducts on re-plan) with no production. Fix: record consumed qty on the plan and credit it back on release (or move consumption to the store/issue step).
- **[Medium] Capacity-conflict detection uses a day-aggregate model that doesn't match per-cell booking** — `src/components/planner/PlannerScreens.tsx:84` — `capacityConflicts()` treats capacity as a flat 9×2=18 slots/day keyed only by date, greedily reserving earliest slots. Flow/impact: it can flag "Won't fit / every shift booked" while specific usable lines are free, and miss genuine per-line clashes — the warning and the actual booking use different capacity models. Fix: model conflicts against the same machine×shift×date grid the modal uses.
- **[Low] Old planning UI mislabels order quantity as kilograms** — `src/components/Planning.tsx:165` (also 241, 297) — renders `quantity ... kg`, but `SalesOrder.quantity` is unit-typed (types.ts:42) and the planner screens treat it as "units". Flow/impact: the same order shows "5,000 kg" one place and "5000 units" another. Fix: one unit, labelled consistently.

## Manufacturing & Logbook Flow

- **[Blocker] Draft logbook edits are never persisted — only Submit&lock writes state** — `src/components/LogbookModule.tsx:231` — All field edits update local `activeLogbook` only; the sole writer to `setMachineLogbooks` is `handleSubmit` (line 293), and the `selectedPlanId` effect reloads from `machineLogbooks` (231) — no autosave, no "Save draft". Flow/impact: an operator who fills half a shift then switches the plan dropdown, changes tab, or leaves the module loses everything with no warning — a whole shift of readings gone. Fix: debounced autosave upserting `activeLogbook` (status `draft`), or a "Save draft" action, plus an unsaved-changes nav guard.
- **[Blocker] The only seeded scheduled plan already owns a submitted/locked logbook — operator lands read-only with no way forward** — `src/mockData.ts:215` — `plan-1` is the single `scheduled` plan and `initialMachineLogbooks[0]` (`log-101`) is already `submitted` against it; `locked` (261) makes every input readOnly and disables Submit and Clear (`handleNew` early-returns when locked, 302). Flow/impact: on first load the Logbook is a frozen historical sheet; the operator can't start a new shift log, and one-plan→one-logbook means no "new shift logbook" affordance. Fix: seed the scheduled plan without a submitted logbook; allow a fresh draft per shift/date even when a prior submitted one exists.
- **[Blocker] Submit validates only the finished-roll register — but that register flows nowhere; QA reads traceability rows, which submit never validates** — `src/components/LogbookModule.tsx:286` — `handleSubmit` blocks only on `rolls.length === 0`, yet `logbook.rolls` is consumed only here + `GuidedPreviewSheet`; QA derives its queue from `traceabilityRows.lotNumber` (`QualityPacking.tsx:157`). Flow/impact: the one required field (rolls) is a dead end that never reaches QA/Inventory/Dispatch, while the data QA actually reads (packed lots, signatures, temps) can be blank at lock. Fix: flow `rolls` into the QA/packing queue, or validate+submit on `traceabilityRows`/production totals; unify the two roll representations.
- **[High] Operator role screens write an isolated in-memory store, disconnected from the logbook and never persisted** — `src/lib/operatorStore.ts:14` — HourlyGrid/MyLine/MyShiftSummary read/write module-level `rows`/`breakdowns` for a hardcoded `MACHINE='M08'`, which is neither in `machineLogbooks` nor the `/api/data` payload. Flow/impact: hourly readings on the touch grid vanish on refresh and never populate `hourlyInspections` or reach Quality; the operator's line is `M08` while the only scheduled plan is `M04` — two "manufacturing" surfaces describing different machines. (Breakdowns are the exception — shared with Maintenance.) Fix: back the operator grid with the same `machineLogbooks` state keyed off the plan's machine, and persist it.
- **[High] Lock is irreversible and submit has essentially no completeness validation** — `src/components/LogbookModule.tsx:284` — Submit checks only `rolls.length>0`; no check for signatures, traceability, out-of-range temps, or required params, and nothing ever sets a submitted logbook back to `draft`. Flow/impact: an operator can permanently lock an ISO logbook with blank sign-off, empty traceability, and unresolved amber OOR values; a supervisor spotting an error post-lock has no correction path. Fix: gate submit on the fields downstream needs, and add a supervisor "reopen".
- **[High] QA roll queue pulls from ALL logbooks with no submitted-status filter** — `src/components/QualityPacking.tsx:157` — the comment says "all submitted logbooks" but the `flatMap` applies no `status==='submitted'` filter. Flow/impact: traceability rows from unlocked drafts leak into the Quality queue, so QA can "pass" rolls off a shift still mid-entry and unsigned. Fix: `machineLogbooks.filter(l => l.status === 'submitted').flatMap(...)`.
- **[Medium] The operator logbook always uses template[0]; the plan's product/order never selects the template** — `src/components/LogbookModule.tsx:202` — `templateForPlan()` returns `templates[0]` (192) and the template selector lives only in the Admin tab. Flow/impact: an LDPE-coil order (`QR/MFG/012`) still gets the SPVC `QR/MFG/013` sheet with wrong zones, coil specs, and rejection reasons. Fix: resolve the template from the plan's product / machine `logbookFormat`, not `templates[0]`.
- **[Medium] ManufacturingStandards is a decorative silo — OEE is a slider, BOM is a re-typed island, shared mfg utils are dead code** — `src/components/ManufacturingStandards.tsx:223` — OEE is `avail*perf*qual` from three sliders (never reads logbooks/breakdowns/yields); `BOMRecipe`/`BOMItem` are re-declared locally (30-42) separate from `types.ts`; `src/lib/mfgUtils.ts` is imported only by a test. Flow/impact: OEE/yield shown to users are hand-cranked; editing a BOM here changes nothing in planning/costing/issue. Fix: compute OEE/quality from real logbook+breakdown data via `mfgUtils`; unify BOM with Planning's formulation model.
- **[Medium] "Clear draft" mints a new logbook id, so a later submit duplicates the plan's logbook** — `src/components/LogbookModule.tsx:40` — `blankLogbook` sets `id: log-${Date.now()}`; `handleNew` (302) makes a fresh-id blank and `handleSubmit` upserts by `id` (293), so submitting after Clear prepends a second logbook with the same `productionPlanId`. Flow/impact: duplicate logs per plan; the reload `find(...)` returns only the first, and QA's `flatMap` shows rolls from both. Fix: key the draft/upsert on `productionPlanId`, or reuse the existing id when clearing.
- **[Medium] Derived totals silently overwrite manually-entered Production Report cells** — `src/components/LogbookModule.tsx:264` — `withDerived` recomputes `totalRollsProduced/totalRollKgs/rejectionKg/totalConsumedKg` on every roll add/remove, while the sheet also lets the operator type those cells, and QA later overwrites `rejectionKg` again. Flow/impact: an operator filling the report as on paper loses those figures the instant a roll is registered; MD/Dashboard/Reports read the clobbered scalars. Fix: make derived cells read-only, or pick one source of truth per field.
- **[Low] "Scanned physical sheet" attachment is a dead affordance** — `src/components/GuidedPreviewSheet.tsx:236` — the preview branches on `l.attachedImage` (defined `types.ts:234`) but nothing assigns it. Flow/impact: permanently reads "No physical sheet image attached". Fix: add a file input storing the image on the logbook, or remove it.
- **[Low] My Line headline numbers are fabricated, not derived** — `src/components/operator/OperatorScreens.tsx:78` — "Rejections (kg)" is hardcoded `"0"`; produced kg is `1240 + rolls*7.8` from the simulation, not any logbook entry. Flow/impact: shift production/rejection totals are decorative and can contradict the logbook. Fix: compute from the roll register / rejection counts.

## Quality, Inventory & Store Flow

## The value chain — where each handoff breaks

The ERP's promise is one continuous thread: **Enquiry → Quotation → Order → Plan → Logbook → QA → Inventory → Dispatch → Trace**, with Complaints/CAPA closing the loop. Here is where that thread actually holds and where it is cut:

| Handoff | Status | Why |
|---|---|---|
| Customer → Inquiry → Quotation → Order | ✅ Works | Shared lifted state; consistent status strings |
| Order → Production Plan | ✅ Works | `pending` order appears in Orders-to-Plan; plan flips it to `planned` |
| Plan → Logbook (gating) | ⚠️ Wired but broken | Plan gates the logbook, but the seeded plan is pre-locked and the template is always `[0]` |
| Logbook → QA (roll queue) | ❌ **Cut** | QA reads a hardcoded 5-roll seed / draft-leaking traceability rows; produced rolls never arrive |
| QA pass → Inventory (FG stock) | ❌ **Cut** | Pass books no FG receipt; two stores share no state |
| Inventory/put-away → Dispatch | ❌ **Cut** | `stored` pallets never become `ready`; only the seed pallet is dispatchable |
| Dispatch → Order status / ledger | ❌ **Cut** | Release updates a demo ticker, not `salesOrders`/`dispatches` |
| Any stage → Batch Passport (trace) | ❌ **Cut** | Passport is a static 2-lot lookup; live IDs return "No record found" |
| Complaint → dispatched batch → CAPA → close | ⚠️ Partial | Batch is free text; CAPA close bypasses required fields |

**The single most important takeaway:** the *front half* of the business (sell → plan) is genuinely connected; the *back half* (make → inspect → store → ship → trace) is a set of well-built screens that don't pass data to each other. A production system is exactly that back-half thread.

**Deferred by design — these need a product decision, not a patch:**

- **Real credential authentication.** The app's identity model is role-pick *by design*. True login (passwords/SSO + server sessions) turns the demo into a different product — left for you to greenlight before I build it.
- **Server-side authorization.** No user session reaches the Express store, and the Firestore path uses the client SDK. Genuine enforcement needs real sessions/claims. Client `can()` therefore stays **cosmetic by design** — flipping it to default-deny adds no real security and would disable the action buttons that six leaf screens gate through `useCan()`.
- **Per-role Firestore rules.** Rules are `auth != null` per collection; per-role rules require Firebase **custom claims**, which the client-side role model never emits. Editing rules I can't deploy or test would risk breaking sync for no verifiable gain.
- **Same-record concurrent edits.** Two users editing the *same* collection within the 1-second window is still last-write-wins; full resolution needs an optimistic-locking (rev/version) protocol on both client and server.

## Prioritized remediation roadmap

Fix in this order — each phase is a prerequisite for the next being meaningful.

**Phase 0 — Decide the architecture (before any code).** Two things must be settled first because half the bugs are symptoms of them:
1. **One store per domain.** Delete the losing side of every duplicate (`SalesModule`/`Customers`, `Planning`, `QualityPacking`/`InventoryModule` monoliths vs the role screens, or vice-versa). Today the same record is edited by two code paths with different rules — no fix survives while both exist.
2. **One persistence backend with real auth.** Pick Firestore *or* the Express `data.json` API, put authentication in front of it, and scope data per tenant/user. The current dual, unauthenticated, world-writable setup cannot be incrementally hardened.

**Phase 1 — Security & data-integrity blockers (do not ship without these).**
- Real authentication; stop hardcoding Google users to Managing Director (`App.tsx:298`).
- Server-side authorization on every read/write; treat client `can()` as cosmetic (`accessStore.ts`, `firestore.rules`, `server.ts`).
- Fix the concurrent-save clobber (record-level patch, not array replace) and single-writer the shared blob (`server.ts:218`, `ManufacturingStandards.tsx:181`).
- Remove committed secrets/identity, gitignore `data.json`.

**Phase 2 — Reconnect the back-half value chain (makes it an ERP, not a demo).**
